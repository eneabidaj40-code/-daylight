# Daylight scheduling fixes — review report

Prepared locally on 28 October 2026. No commit, push, repository settings change, or deployment was performed. Browser fixtures use separate contexts and localhost origins; the deployed application's storage was not opened or changed.

## Root causes and resulting behavior

1. **False class/exam overlaps:** recurring classes were materialized using only weekday, interval, and semester dates. There was no academic-calendar exclusion. The same false occurrences then created travel and recovery blocks and occupied study time. [academic.ts](./src/academic.ts) now supplies one suspension predicate used before materializing classes or campus trips. Period endpoints are inclusive local calendar dates in the configured timezone. Overlapping periods are evaluated once per date. The original timetable remains stored, including its biweekly anchor and semester boundaries.
2. **Generation could appear unresponsive:** the click handler existed, but the planner ran synchronously during the proposal panel's initial render and on regeneration, without a loading/error boundary for generation. Changing the date or range left the old plan active. Empty results lacked specific diagnoses. [Planner.tsx](./src/Planner.tsx) now opens a dedicated proposal panel, yields to display loading, catches generation errors, invalidates stale input, and explains missing subjects/topics/future exams, blocked commitments, elapsed waking windows, fulfilled workload, and daily ceilings. Each suggested session shows its reason and timing.
3. **Exam-time cutoff:** priorities were calculated once per day and reused for all its free slots. Exam-only preparation could continue after the exam's exact start time. [schedule.ts](./src/schedule.ts) now recalculates eligible priorities at each slot, uses exact remaining hours for urgency, and clips exam-only preparation to the exam start. Topics remain eligible afterward when still unfinished. Recommendations rise toward exams within the existing workload and configured daily ceiling.
4. **Approval was not a durable acknowledgement:** acceptance appended fresh random event IDs to React state and reported success before asynchronous IndexedDB autosave completed. It validated a rendered snapshot and had no persistent acceptance receipts. [proposals.ts](./src/proposals.ts), [persistence.ts](./src/persistence.ts), and [store.tsx](./src/store.tsx) now validate against the latest saved workspace and atomically write calendar events plus receipts. Stable proposal event IDs, receipt checks, serialized transactions, and an immediate click latch prevent repeated/partial acceptance from duplicating events. Success appears only after transaction completion. Errors remain visible and can be retried. Confirmed activities are never rearranged by generation.
5. **Return commute assumed immediate departure:** return travel always began when the last recurring class ended, using one global duration. Weekday rules and date overrides now support either a fixed bus departure or a waiting interval, separate return duration, and an optional same-day arrival-home time. Waiting occupies time. Departure never precedes the last campus commitment. Recovery and study availability use the resulting arrival. Incompatible bus/arrival settings produce warnings instead of negative travel intervals.
6. **Rejection and navigation:** rejecting used to write historical rejected-day metadata. New rejection changes no workspace records. “View calendar” now opens the accepted session's date and resets the calendar's internal tab so it works when planning from Academic calendar.

## Using the changes

- Open **Calendar → Academic calendar**. Add “Midterm Week”, “Final Exam Week”, or other named periods. Both the global suspension preference and each new period's suspension switch default to enabled. Classes resume automatically after the last active suspension ends. Personal activities and independently scheduled university activities stay visible and occupied.
- Add return rules for different weekdays. Use a date override for a one-time trip; it replaces that weekday's rule. Travel-to-university and the fallback travel-home durations remain independently configurable in Settings. No class timetable edits are required.
- Existing exams do not acquire assumed travel requirements during migration. In the exam editor, explicitly select **This exam requires university travel** when a trip is needed. An independent activity has the corresponding university-trip checkbox. These campus commitments can create a trip during a suspended week; a return rule alone cannot create a trip.
- Choose **Generate Study Plan** from Dashboard, Calendar, or the mobile Plan action. Review daily recommendations and individual reasons. Modify, regenerate, reject, accept one study session with its following break, or accept all remaining suggestions. Accepted rows become read-only. A newly generated plan respects already confirmed study.

## Database migration and preservation

The database name remains `daylight-private-planner`; the object store remains `workspace`; the active record remains `state`. Physical database and workspace schema versions advance from 1 to 2.

The versioned, additive migration adds empty `examPeriods`, `commuteRules`, and `acceptedSuggestionIds` collections and defaults `settings.suspendClassesDuringExamPeriods` to `true`. Optional `requiresUniversityTrip` flags preserve prior behavior when absent. All existing subjects, topic workload, grades, assessments, exams, activities, workout templates/exercises, completions, prior semesters, rejected-day history, and settings remain compatible. Version 1 JSON imports are upgraded through the same validation path; version 2 imports also work.

Before replacing a valid version 1 payload, the same transaction stores its untouched original at `workspace/migration-backup-v1`, only if that backup is absent. The backup and migrated state commit together. A validation, quota, or transaction failure aborts both writes. An unreadable or unsupported workspace produces a recovery screen instead of a blank replacement. There is no automatic data clear, sample-data load, or reset.

An old open Daylight tab can block the physical database upgrade. Close other old tabs/installed windows and retry when instructed; do not clear browser storage. Once migrated, use the updated application. The older binary expects database version 1.

## Limits

- Desktop Edge and phone-sized Chromium layouts are automated; a physical iPhone/Safari installation has not been tested. Offline browser reopening is verified, not an on-device Safari process restart.
- Commuting models one campus round trip per day, from the first to the final campus commitment. A manually entered arrival uses the same local calendar date; calculated travel/recovery may cross midnight. It does not fetch live bus timetables. If the requested bus departs too early, the app clamps departure to the last commitment's end and asks you to check the next bus.
- Unaccepted proposals live in the open panel. Generate again after closing/reloading. Accepted sessions and their duplicate-prevention receipts persist.
- Workload, topic completion/confidence and exam preparation remain user-maintained estimates. Study recommendations do not predict grades.
